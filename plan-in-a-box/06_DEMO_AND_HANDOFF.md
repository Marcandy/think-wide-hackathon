# Demo, work brief, and post-work learning

## Show the context boundary, not another code editor

The live question must require comparing at least two repositories. Use real permitted snapshots, possibly newly created during the event and clearly labeled as demonstration repositories. Synthetic data is fine when disclosed. Do not claim fabricated files are from the user's historical projects.

Suggested narrative: two repositories contain superficially similar command handling. One has a reusable contract; the other depends on a permanent worker. Ask whether a third planned project can reuse the contract without adopting the runtime. Inspect the actual evidence. Correct the agent's initial applicability assumption. Reopen the saved investigation, then generate the brief.

A meaningful correction changes the accepted comparison or plan. Changing only a badge/title is not sufficient. A canned "no worker" branch without live reasoning is not an agentic result. The demo can be rehearsed; the underlying source and driver status must remain honest.

## Three-minute recording shape

| Segment | Show |
|---|---|
| Opening | The global question and selected repositories/snapshots |
| Discovery | A compact map/search result, then an exact cited implementation span |
| Intervention | Human says to reuse contract only and rejects the runtime assumption |
| Adaptation | The decision persists and the agent changes its comparison/brief |
| Continuity | Reopen or use a second tested client to retrieve the same decision/evidence |
| Handoff | Export the implementation brief, or show its real approved GitHub issue receipt |

At 15:00 preserve the first complete recording, source commit, config/auth/data mode, actual host/provider, and which capabilities were disabled. Never overwrite that recording. Re-record at 16:20 only if better; keep both. A recording is labeled recorded, not live. If the first complete path is still absent at 15:00, stop optional work and record the actual partial state separately.

## The implementation brief is the output object

Use a small structured record with a deterministic Markdown presentation. It is not a new task-management product. GitHub Issue and private download are representations of the same frozen brief revision.

An issued brief contains:

- Objective, intended target repository, exact base commit, and desired observable result.
- The accepted constraints and prior rejected approaches, with their source/decision identities.
- Relevant cross-repo evidence with exact refs and concise applicability notes.
- Likely files as a suggestion, explicitly not a verified complete dependency list.
- Acceptance behavior and tests the specialist should run; mark which have not been run.
- Allowed editing scope, excluded changes, budget/approval requirements where relevant.
- Missing evidence, stale dependencies, and uncertainties that must be checked locally.
- Investigation/handoff ID, revision, prepared-at time, source snapshot identities, audience, and body hash.

Do not export the whole chat or every repo. The specialist can call Think-wide tools to expand exact evidence. An exported reference is not a capability to access private data; the receiving agent/user must authenticate and have the relevant grants.

**Approval for publishing an issue is not approval for the coding agent's future code changes.** The specialist works under its own repository access and human instructions. Think-wide does not control the specialist's model, tools, environment, or hidden context.

## Optional GitHub publication

Before POST, show the exact destination, title, body, and source/audience implications in the owned human confirmation path. Bind approval to the frozen revision/hash and reauthorize all inputs immediately before effect. Exclude provider tokens from the brief.

If provider integration is unavailable at 15:30, preserve the exact Markdown body and let an authorized human publish manually. Mark it exported, not published. A manually created issue can later be attached after its identity/body are verified; do not assert the service created it.

## Read-only outcome ingestion

Later, a user selects the resulting commit/PR/issue. Validate that it belongs to the permitted repository and relates to the handoff. Read its actual diff and provider state. Distinguish author-reported tests, CI status, observed merged state, and Think-wide's interpretation. Closed PR does not mean merged; green CI does not prove the whole objective.

Store an outcome link and a proposed learning update. Do not automatically promote "this pattern is reusable" into a universal verified fact or delete the older decision. Human correction can revise applicability. This path uses the same index/evidence machinery; no repair executor returns through the back door.

## Final claims checklist

For each claimed capability list implemented commit, acceptance case, tested environment, and status. Hosted WorkOS, GitHub App connection, remote MCP tool use, native embedded UI, backend reasoning, issue POST, outcome ingestion, deployment, and recovery are independently marked. One real host pass does not prove all hosts.

Ensure the public submission repository contains only permitted code/docs/fixtures, not imported private source or credentials. Identify event-day work versus libraries, prior design, and other prior assets. Submit only after a human reviews the actual final result and required organizer disclosures.
